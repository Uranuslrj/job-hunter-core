# 落地说明：这个框架在本地怎么跑起来

> 框架定义（README.md / orchestrator.md）和领域配置（domains/*/domain.yaml）已经齐了。
> 这一页讲：怎么用我（WorkBuddy 本地）把"执行者 + 批判者"真正跑起来，而不是停留在文档。

---

## 一、关键认知：框架是"流程约定"，不是"代码"

这套多 Agent 框架，本质是**一套固定的协作流程 + 每个角色的职责/输入输出/停止条件**。落地方式有两种，你选了第一种：

- **方式一（你选的）**：用我本地的子代理。执行者、批判者各是一个子代理，我作为"人"的角色在中间调度和裁决。
- 方式二：写成独立 Python 脚本（更重，暂不做）。

所以"落地" = **把这套流程约定，固化成一个随时可调用的运行方式**，而不是写一堆新代码。

---

## 二、怎么跑一次（一个任务走一遍）

以"投简历"领域为例，你丢给我一条 JD，我按框架跑：

```
你：帮我用多Agent框架，分析这条JD该不该投
我：
  1. 启动【执行者】子代理 → 收集+比对 → 产出结构化方案（含依据+来源）
  2. 启动【批判者】子代理 → 用 domains/job_application/domain.yaml 的两套清单挑刺
     → 有缺陷 → 打回执行者改（最多2轮）
     → 无缺陷 → 通过
  3. 把「方案 + 缺陷清单」一起给你
  你：拍板（用/改/弃）
```

**你只需要说一句"用多Agent框架跑这个任务"**，剩下的是我把两个子代理按框架串起来。

---

## 三、批判者怎么"有外部抓手"

这是框架里最关键的一条，落地时要兑现。批判者不是"凭感觉挑刺"，而是：
- 拿 domain.yaml 的 `external_anchors`，去**真的核对**（比如打开来源 URL 看存不存在、比对 JD 原文）。
- 拿 `rulebook`，逐条对照输出有没有踩线。

**没有外部抓手的地方，批判者不许下判断**——这是铁律。

---

## 四、换领域怎么操作

1. 复制 `domain_template.md` → `domains/<新领域>/domain.yaml`
2. 填三样东西：外部抓手、指标清单 A/B、规则手册
3. 跟我说"用多Agent框架跑这个任务，领域是 <新领域>"，我用新领域配置跑。
